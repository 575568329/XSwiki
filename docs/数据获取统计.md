# 小说数据获取方法统计

> 两本书实战总结（2026-10-21 ~ 10-23）。核心结论：**获取通道选对，成本差一个数量级**。

## 〇、新书接入决策流程（先读这个）

拿到一本新小说，按顺序判定，命中即停：

1. **搜现成 wiki 生态**（成本最低）：GitHub / Fandom 搜"`{书名} wiki`"、"`{书名} skill`"。有镜像仓库 → 走**通道 A**（当天可出全库）。诡秘之主（`scaret/lord-of-mysteries-skill`）与凡人修仙传（`Lizhenghe-Chen/fanren-wiki`，七库资料站全量数据内嵌 index.html）即此路径，均 0 个扫描子代理。
2. **同步抓百科词条卡做权威核对**：用下方开放接口批量拉人物词条（`analysis/guimi/grab-baike.mjs`），与 wiki 数据交叉修正。
3. **补体系/设定**：书有人工维护的 wiki 站（如玄鉴之于 9433.com.cn）→ 走**通道 B** 定向抓单页存档。
4. **兜底：抓原文自己提取**（成本最高但全覆盖）：以上都没有、或要章号剧情线/原文证据/龙套 → 走**通道 C** 全文抓取 + roster 扫描。书源列表参考 `https://www.luoxx.top/book_source.txt`（77 源 JSON，含各站选择器规则）。

多数书是 **A+B 组合**（wiki 出人物库、百科/wiki 站做核对）；纯冷门书才需要 C。

## 一、三条获取通道（按成本从低到高）

### 通道 A：百科开放接口 + wiki 镜像仓库（首选，诡秘之主实测）

**百度百科开放接口——无风控，可直接 curl/node fetch**（公司内网也通）：

```
https://baike.baidu.com/api/openapi/BaikeLemmaCardApi?scope=103&format=json&appid=379020&bk_key={名字}&bk_length=60000
```

- 返回 infobox（字面量键值）+ abstract，一次请求一个词条；歧义名靠 desc 字段校验剔除（如"阿蒙"→吕蒙）
- 注意与百科主站区别：**主站 curl/WebFetch 403**，早年用 IAB 浏览器自动化抓；开放接口出来后 90% 场景不再需要浏览器
- 实现：`analysis/guimi/grab-baike.mjs`（批量+断点，failed.txt 记录未命中）

**Fandom wiki 的 GitHub 镜像仓库**（用户/社区已做好结构化，直接 clone）：

- 诡秘之主：`scaret/lord-of-mysteries-skill` = Fandom 中文 wiki 同步库，645 词条（角色 273 + 途径 53 + 势力 42 + 神祇 63），markdown 内含尊名/化名/身份/外貌/性格/名台词结构化段落
- 玄鉴仙族参考：`TuYv/xianzu-wiki`（290 人 + 228 关系边，JSON 与本项目同构，153 条结构化关系边直接吸收）
- 选型思路：做书之前先搜"`{书名} wiki github` / `{书名} skill`"——LLM 生态常有现成同步库

**成本对比**：诡秘 310 人全程 **0 个扫描子代理**（仅 T1 28 人在主会话内嵌精修）；玄鉴 793 人全文范式用了 ~30 个子代理调用、每窗 40-90 万 token。

### 通道 B：权威 wiki 站点定向抓取（补充体系/设定）

- 玄鉴修为体系以 9433.com.cn 玄鉴仙族Wiki 为权威源（六境顺序、释修线、果位称谓），存档 `analysis/wiki-cultivation-system.md`
- 适用：书没有现成镜像仓库，但有人工维护的 wiki 站。抓单页存 md 即可，不必全站

### 通道 C：盗版书源全文抓取（兜底，人物库全量覆盖唯一手段）

wiki/百科只有"有名有姓"的人物；**龙套与剧情线必须读原文**。玄鉴范式（570 万字实战）：

1. **书源探测**：77 源 JSON（`analysis/book_source.txt`，含各站 CSS 选择器 + 广告过滤正则）。公司网关按 URL 分类拦盗版站：**http 返回 2578 字节拦截页（HTTP 200！），https 掐 TLS（curl 35）**——可达性必须内容级验证（size>5000 且不含拦截页关键词），http/https 都试。GBK 站 searchkey 要 GBK 编码。同一书留 2-3 源交叉验证
2. **实测可用站**（2026-10）：爱书包 shubaoge.org（主源，1636 章）、得奇 deqixs.org（修复源）、UU uuwx.la（正文实际是 `#content`，书源规则写的 `.box_box` 已失效——**选择器必须 curl 一章人工核对**）
3. **抓取**：并发 ≤6、UA 带 Chrome 串、失败退避重试 4 次、`store.ndjson` 追加式断点续传（1636 章 71 秒）
4. **章节真伪校验**（必做，四类全查）：

| 问题 | 检测 | 修复 |
|---|---|---|
| 假章（内容错位复制） | 章节中段 1k 字符 md5 去重 | 从第二书源重抓区间 |
| 占位章（"正在手打中"） | 正则扫全文，正文 100-200 字 | 多源重抓；上游共缺则登记接受 |
| 跳章/重号 | 章号解析找 gap/dup | 他源补或登记 |
| 防盗字符替换 | 稀有字频率统计 | 量小（<100/500万字）不管 |

   玄鉴战果：866-895 段假章（书包站复制 838-865 正文）得奇源修复；42 个占位章修复后遗留 36 个；1460-1496 全网盗版源缺失（起点正版独有），共占全书 2.2%

5. **抓取脚本内存安全规矩（2026-10-23 实测撑爆过内存，写脚本前必读）**：①正文节点必须先剥 `script/style/ins` 再 `.text()`（`getCookie` 等内嵌 JS 混进正文，既污染数据又不可控）②正文四重校验：长度 / 开头汉字 / JS 关键词黑名单 / 汉字占比 ③断点索引只存 URL 不存正文 ④响应流式限长（>3MB 即弃）⑤并发 ≤3 ⑥进度日志带 heapUsed。参考 `analysis/guimi/fetch-guimi-text.mjs`（诡秘 1454 章 148 秒，heap 稳定 <35MB）；诡秘可用源：yunxs.la（主，1454 章）/ cxzz958.com / 77shuku.org；凡人：yunxs.la（2362 章，**目录标题脏形态多**——缺第字/卷名+章名/夹通告，要按含章号模式+公告黑名单+章号去重过滤，正文 2446 章上游缺 ~84 章）
6. **原文入库（阅读器）【已停用 2026-10-23，阅读功能移除；原文抓取仍用于通道C人物提取管线，只是不入库不阅读】**：`build-text.mjs` → `plugin/data/text/<bookId>/t{N}.json`（150 章/块 ≈1.6MB，章内自动分段）+ 书目 JSON 挂 `textIndex`（chunks/count/titles）；前端"原文"Tab 按需拉块、记忆进度。热更新包**不含** text 块（gen-manifest 只收书目 JSON），原文随插件内置；uTools 端新书原文需随包更新（懒下发为 backlog）

## 二、原文 → 结构化管线（通道 C 后续）

1. **人名普查**（extract-names.mjs）：姓氏 n-gram 两趟——3 字名 `count≥12 且 count/count(前2字)≥0.5`；2 字名独立计数 ≥15；补显式标记（道号/名为/唤作）。**家族字辈稀释坑**：字辈家族把 3 字名占比拉到 <0.5 系统性漏检，需 roster 确认后全文直扫补统计；2 字字辈前缀（李曦）不是人物
2. **roster 抽样扫描**：全书均分 24 窗（每窗 ~4 万字≈8 章），每窗一个子代理，3-6 并发/批（**>10 并发触发账户限速 1302**），单窗 8-25 分钟；note 要求密集记录（后一趟画像看不到原文）
3. **归并去噪**：roster × 普查交叉；minedOnly 噪声（高频词/称号/地名）、幽灵卡（字辈 2 字前缀、化身穿马甲、称号单列）、世代/势力标签归一
4. **画像卡**：tier1 定向素材（首现 3 章 + 高密度 12 章 + 末现 2 章 ≈ 15KB/人），子代理逐人写卡，硬约束=只用素材证据/evidence 逐字引用/timeline 按章号
5. **交叉核对**：百科词条为权威源跑 baike-check.mjs 三方向核对（族谱/势力/体系）→ baike-fix.mjs 幂等修正集（build-data 后必跑）。玄鉴两轮修正 25+ 处（世代表错位、结局误判、仙基误记）

## 三、wiki 仓库 → 结构化管线（通道 A 后续，`analysis/guimi/`）

1. `parse-wiki.mjs`：解析途径序列表/角色/神祇词条 → guimi-parsed.json；第二部内容过滤（途径组整组剔除 + EXCLUDE 名单）
2. `build-guimi.mjs`：editorial 内嵌精修（T1 28 人事实卡 + 称号 MERGE 表 + redirect 跳过 + 势力成员反查分派）→ 书目 JSON，拼音索引同玄鉴
3. 字段映射：generation=途径正式名（**途径正式名=序列 0 名**，如占卜家途径→愚者途径）、cultivation="序列N 名"、mentions=textLen（资料丰富度）、evidence=wiki 名台词、timeline 空（wiki 无章节数据）

**wiki markdown 三坑**：
- CRLF 的 `\r` 让非多行 `$` 和 `.` 全失效（JS `.` 不匹配 `\r`）——读入必须 `replace(/\r\n?/g,'\n')`；段落前瞻写 `(?=^##(?!#)\s)`（`^## ` 会截断 `###`）
- 模板字符串里正则要写 `\\s`；字面量正则不受影响
- 称号重复词条（"五海之王"纳斯特 等 10 个）不是重定向，要手工 MERGE 表归并；redirect 文件自动跳过

## 四、多体系数据（gen-system.mjs）

- 每本书有自己的境界体系（玄鉴=六境+释修线+仙基；诡秘=22 途径×10 序列五级阶梯），systemPage 数据驱动，前端标题按书切换（仙基图鉴/途径图鉴）
- 释修等亚体系独立成阶梯：身份词匹配必须出现在介绍开头 20 字内（身份定语位置），否则"备注提到释修"的噪声全被误带（39 人口径 → 真实 20 人）
- **位阶词混进花名册的甄别（2026-10-26 玄鉴实证）**："怜愍"实为释修位阶（位阶链：僧侣→法师→怜愍→摩诃）非人物，曾混在花名册里，已删（793→792）；余 8 条"位阶+特征"泛称条目（如七目怜愍/持剑怜愍）待甄别是具名修士还是泛称，不阻塞使用
- **全链重跑纪律**：`build-data.mjs` 之后必须依次重跑 `merge-v2.mjs`（画像卡+势力）→ `gen-system.mjs`（体系页）→ `gen-seals.mjs`（印章）→ `gen-manifest.mjs`（热更新包）——build-data 重跑会覆盖丢失这些产物（已踩过）

  - 视觉质检：glm-4.5v API + base64 直传（MCP analyze_image 只能拉智谱可达域名，第三方 URL 全 1210；`glm-4.5v-flash` 模型名不存在）

## 六、供给前端：热更新（不发版加书）

- server 放 manifest（含每文件 sha256）+ 书目 JSON；插件启动静默检查 TTL 30min + ETag 304（单次 ~300B）；变更才下载（sha256 校验+原子写 `~/.utools-novel-characters/`）；内置 data/ 永远兜底
- **数据 URL 必须内容寻址 `?v=版本-sha前10位`**——纯版本号会被 HTTP 长缓存命中旧文件
- 加书流程：本地跑管线 → gen-manifest → 拷 server/ 到服务器 → 插件自动同步，永不再发版

## 七、平台与环境坑（取数前置知识）

- GLM 1301 内容安全过滤：小说原文大段进上下文会触发，两次打断了会话——**用脚本处理原文，主上下文只放代码与统计**
- 子代理限速 1302：并发 >10 触发；安全 3-6/批，失败小批量重试
- 公司网关：npm 401 用 npmmirror；盗版站按 URL 分类拦截（内容级验证）；多站点直连不可达
- Git Bash 对中文路径 cd 时好时坏——node 脚本内处理中文路径最稳；后台任务路径参数用 ASCII
- 本机无 NVIDIA 独显（本地 SD 排除）
