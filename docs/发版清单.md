## 一、上线时必须处理（按顺序）

### 1. 立绘收尾（前置条件）

### 2. 体积压缩 + AI 标识（同一批次做，最大拦路虎）
- 现状：dist 211MB，立绘占 206MB。官方发布文档**未公布上限数字**，但社区一致反馈开发者工具有 **~100MB 硬限制**——211MB 裸奔必卡，压缩是必选项不是可选项。
- 用最大样张（hupo.png 2.61MB，1024×1024）实测：

| 方案 | 单张体积 | 全量 114 张预估 | 质量风险 |
|---|---|---|---|
| **A. WebP q90（推荐）** | 308KB（11.5%） | **~25MB，整包 ~35MB** | 厚涂渐变基本无感 |
| B. WebP q80 | 183KB（6.9%） | ~14MB | 立绘细节开始软化 |
| C. PNG 256 色量化 | 477KB（17.9%） | ~37MB | 厚涂渐变有断层风险 |
| D. PNG 无损 optimize | 71% | ~147MB | 不够，否决 |

- 样张待验收：`_tmp/compress-sample/`（hupo 原图 / .webp-q90 / .webp-q80 / .png-256c，重点看背景渐变和笔触边缘）。
- **⚠️ 图片同步链路与 JSON 不同**（v1 写错，已修正）：`sync-data.mjs` 只拷 *.json、`gen-manifest.mjs` 只拷书目 JSON，**两者都不碰 images**。立绘的正确链路：`plugin/data/images/`（编辑源）→ 同步到 `plugin-src/public/data/images/` → **vite build** 产出 `dist/data/images/`。`server/data/` 不需要 images（立绘本就不参与热更新）。
- 建议把压缩做成一个脚本（转 WebP q90 + **补"AI生成"角标** + 写入 XMP 元数据，见 §六.1/§六.2，一次批处理同时解决体积与标识），挂在 `gen-images.mjs` 尾部让新图自动走。
- 代码引用点已核实全仓库仅 2 处（`plugin/preload.js:169`、`plugin-src/src/api.js:58` 的 `data/images/${id}.png` 字面量）；`images.json` 存无扩展名 id，不用动。

### 3. 热更新服务器：部署 + 安全加固（地址将随插件公开，加固是必选项）
按 docs/热更新设计.md §五/§六 runbook 部署（安全组 8300 → 防火墙 → 拷 server/ → NSSM 自启 → 办公网 curl 实测），**但 runbook 之前必须先做安全整改**——公开上架后"端口+路径隐蔽"的前提不复存在：
- **部署方式升级（2026-10-29 补）**：同机已有成熟部署规范 `D:\Study\aliyun-ops`（run.cmd 3 秒守护重启、schtasks 自启、日志 10MB 轮转、幂等部署脚本、SERVICES.md 登记）——热更新服务应并入该体系（`aliyun-ops\services\data-server\`），**替代**热更新设计.md 里的手工 NSSM/计划任务步骤，顺带解决运维审阅提出的"崩溃拉起/日志轮转"缺项（tracker-server:9420 已用这套在跑）。
- **修崩溃 bug**：`serve.mjs` 请求回调无任何 try/catch，`GET /%` 使 `decodeURIComponent` 抛 URIError **整进程崩溃且无人拉起**（已实测复现）。包 try/catch + 崩溃自动重启。
- **修客户端路径逃逸**：`plugin/preload.js` 对 `bk.file` 未做 `[\w-]+\.json` 白名单就 `path.join(CACHE_DIR, bk.file)`，manifest 被篡改时可 `..\..\` 逃逸主目录写文件。加白名单一行。
- **鉴权与限流**：⚠️ 热更新设计.md §三 说"serve.mjs 已预留 ?token="**失实**（全文 37 行无 token 代码）——现状是零鉴权零限流。最低配：加 token 校验；同步修热更新设计.md 的表述。
- **带宽费用**：无鉴权下数据可被恶意循环拉取，阿里云按流量计费无上界。配带宽封顶/流量告警/访问日志（serve.mjs 现在只启动打印一行）。
- **信任根**：sha256 由同一明文 HTTP manifest 自带，MITM/服务器被黑即可投毒。中期建议 manifest 签名或迁 OSS+HTTPS（一并消解刷量/投毒/备案问题——大陆 IP 非标端口 HTTP 对外服务属备案灰区）。
- 不发热更新也行：dataServer 留空 `""` = 纯内置数据（preload 返回 skipped 'no-server'，功能不缺），§七.6 拍板。

### 4. uTools 实机回归（dist 拖入开发者工具）

## 四、目录整合方案（治"文件夹一直很乱"）

病根：插件资产 3 份副本（plugin/ 编辑源、plugin-src/public dev、plugin-src/dist 发版），数据另有 server/data 第 3 份；且**数据与插件资产的同步管道不对称**——sync-data 只管 JSON，sync-plugin 管四样，images 只能靠 vite build（public → dist）。

**定死五条规则**（建议写进 docs/README.md 构建纪律行）：
1. `plugin/` = 唯一编辑源，只放五样：`plugin.json`、`preload.js`、`config.json`、`logo.png`、`data/`。旧 UI 删除后它不再具备运行能力（main 字段留着无妨，发版目录从来都是 dist）。
2. 动 preload/plugin.json/config/logo → 必跑 `node analysis/sync-plugin.mjs`（带逐字节校验）。
3. 动数据 JSON → 必跑 `node analysis/sync-data.mjs`；**动 images → 手动同步到 `plugin-src/public/data/images/` + 重新 vite build**（或把 images 纳入一个同步脚本，做 §一.2 压缩脚本时顺手包进去）。
4. 发版包只有 `plugin-src/dist`；`public/` 只服务 vite dev（5173），`preview-dist.js` 只服务浏览器预览（5177）。
5. `analysis/` 分两区：管线脚本平铺根目录，一次性产物进 `analysis/_archive/`（救 486MB）。

## 五、uTools 数据存储方案（治"没有保存数据"）

官方两条路（[数据库文档](https://www.u-tools.cn/docs/api-reference/db.html)）：`utools.dbStorage`/`utools.db` 单条 **≤1MB**、开启同步后**跟随 uTools 账号跨设备**；大文件走插件本地数据目录（不同步）。

现状盘点：防剧透开关、阅读进度、每页条数全存 **localStorage**（`cq.{bookId}.spoiler`、`cq.{bookId}.progress`、`cq.pageSize`）——uTools 实机 webview 的 localStorage 持久性**没有官方保证**，是最可能的丢数据点；热更新记账在 `~/.utools-novel-characters/state.json`（已双会话实测持久，但换电脑不跟随）。

| 数据 | 现状 | 建议 |
|---|---|---|
| 防剧透/阅读进度/每页条数 | localStorage（持久性无保证） | **迁 dbStorage**（<1KB，跟随账号） |
| 热更新记账 state.json | 用户主目录文件（已实测持久） | 可选迁 dbStorage（<10KB） |
| 书数据 JSON（1~2MB/本） | 内置 + 缓存文件 | **不迁**（超 1MB 单条上限，文件是正解） |
| 立绘图片 | 内置 data/images | 不迁（同上） |

**迁移方案（v2 修正版）**：审阅发现 v1 的"preload 加桥、init 里调"有时机 bug——`CharacterList.vue:8` 在组件 setup **顶层同步**读 pageSize，早于 `App.vue onMounted` 里的 `svc.init()`，桥还没就绪就读了。改法二选一：
- **A（推荐，最简）**：UI 侧直接用 `window.utools?.dbStorage ?? localStorage` 做一个 `settingsGet/settingsSet` 小工具（uTools 环境里 `window.utools` 在 setup 时已注入，无需等 init），替换 4 处读写点（`store.js:33-40`、`CharacterList.vue:8/51`），浏览器预览自动降级 localStorage。
- B：仍走 preload 桥，但组件内把初值读取改成 `await svc.init()` 之后的惰性初始化——改动面更大，不推荐。
- 注意 `utools.dbStorage` 单条 1MB 上限对这几个键完全够；书数据/图片永不进 db。

## 六、合规与审核风险（按整改优先级重排）

1. **AI 标识——去水印是已发生的暴露（P0）**：《人工智能生成合成内容标识办法》（2025-09-01 施行）禁止**恶意删除、隐匿 AI 标识**；`analysis/` 里的 `remove_wm.py` 无痕去除豆包"AI生成"角标且 114 张成品已进发布包——这是"已做错的动作"不是"没做的动作"。**整改=补标识**：在 §一.2 的压缩批次里给每张图加"AI生成"角标 + 写入 XMP 元数据（显式+隐式两级标识一次满足），个人非商用量级下这是低成本出路。
2. **"介绍页声明一句"不满足标识要求**：办法要求显式标识加在**内容本身**（角标/水印）、隐式标识写**文件元数据**，介绍文案两样都不算——声明句仍建议写（进 description），但只是辅助。
3. **书目 summary 是百科词条导语逐字复制**（实测诡秘 ~400 字、斗破 ~362 字，未署名）：重写为自撰梗概 + 页脚"资料整理自百度百科/Fandom 等公开资料"声明，约半小时。
4. **立绘属受版权保护角色的 AI 演绎**：个人非商用被追诉概率低，但 uTools 开发者协议要求开发者保证不侵权且责任自担。低成本减险：介绍加"非官方同人作品，立绘为 AI 生成演绎形象，与原作权利人无关"，并预设"收到投诉即下架对应书数据"的响应动作。
5. **定位冲突**：README 10-23 拍板"仅个人本地使用，不分发上架"与本次发版冲突——更新定位声明并在 docs/聊天记录整理.md 留痕；顺带删掉 README 里"逐字原文证据"的宣传表述（放大版权暴露）。
6. **服务器面**：明文 HTTP + 大陆 IP 非标端口无备案属灰区 + 公开后 IP 随插件分发（§一.3 的加固与 §七.6 拍板覆盖）。
7. **引用面（健康，维持现状）**：evidence 逐字引用实测 78 人共 ~8.5k 字、单条最长 166 字，属《著作权法》"适当引用"量级；守住"原文 text 功能不回潮"的既有拍板即可。
