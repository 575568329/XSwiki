> 本文档只做设计，不含实现；实现前需确认优先级。

## 二、读者真正关心什么（按频率排序，家族修仙文语境）

1. **"这谁啊？"速答** — 读到 800 章忘了一个配角：搜名字，3 秒内要知道 ①一句话身份 ②和主角/李家的关系 ③上次出场在哪章。这是最高频场景。
2. **世代谱系** — 李家 11 代字辈，"李遂宁是李周巍什么人"这类问题。家族文读者第一刚需。
3. **谁死了** — 本书死人极多。"XX 死没死"是高频疑问 → 但对没读到的人是剧透。
4. **修为/境界** — 现在什么境界、走的什么道统（明阳/太阴）、仙基是什么（本书特色力量设定）。
5. **阵营版图** — 越国三宗、李家、宋廷、明阳/北寰等道统的关系：谁跟谁一伙。
6. **出场轨迹** — "这人后期还出场吗"：首现/末现章节 + 密度曲线。
7. **人物好看吗** — 立绘（基调待定，暂停生成）。

## 三、信息架构：四个分类页

### 3.1 人物卡（改造重点）

现状问题：字段平铺、status 直接暴露剧透、缺少"速答"视角、无力量体系归位。

新结构（自上而下）：

```
┌────────────────────────────────────┐
│ [立绘]  李曦明  昭景真人·七公子     │  ← 立绘(可选) + 正名 + 最常用别名
│         李家7世·曦字辈·首脉嫡长    │  ← 世代徽章链
│ ───────────────────────────────── │
│ 速答区（永远直接可见）              │
│   一句话: 道号昭景的紫府真人，     │
│   李家首脉嫡长，长年替家族周旋     │
│   诸道统、谋取机缘                 │
│   与主角线: 李家实际的顶梁柱，     │
│   陆江仙最重要的"合作伙伴"          │
│ ───────────────────────────────── │
│ ▸ 档案（收起）性别/身份/势力/      │
│   修为/仙基/道统/结局(防剧透)      │
│ ▸ 力量体系（收起）境界阶梯位置图   │
│   + 成长轨迹（练气→胎息→…→紫府）  │
│ ▸ 关系网（默认展开）               │
│   局部力导向图 + 列表双形式        │
│ ▸ 剧情线（收起）章号时间轴         │
│ ▸ 原文摘录（收起）                 │
└────────────────────────────────────┘
```

关键设计决定：
- **速答区**：oneLiner + 新增 `toProtagonist` 字段（与主角线的关系一句话）——这是"3 秒法则"的载体
- **防剧透**（fanren-wiki 模式）：结局 status 与 timeline 后半段默认打码（`blur`），点击"我已读过/显示"才显现；书目级开关"剧透模式"
- **力量体系归位**：修为不再是孤立文本，拆出 `cultivationStages: [{chapter, stage}]`（成长轨迹），在"力量体系"页有全局阶梯对照
- **关系网局部图**：卡内嵌该人物的 1 度关系力导向小图（≤30 节点），节点点击跳卡

### 3.2 世家页（李家为主，可扩展萧家/陈家等）

冰火维基模式 + 红楼家族树：

- **世代纵表**（核心视图）：11 行（木→…→阙字辈），每行 = 世代徽章 + 该代全部成员（点入人物卡）；行内标注家主/真人（境界着色：紫府金、筑基蓝、练气灰）
- **家主世系线**：木田→项平→玄宣→渊蛟→曦城→周巍→…竖向主干高亮
- **家族档案**：发源地（黎泾村）、现状、依附/盟友势力、族内大事记（章节锚点）
- **女眷说明**：女子用字辈不同（渊清辈/曦月辈）需在世代表旁注明"同辈"

### 3.3 势力页

- **版图/阵营分组列表**：李家（仙族）｜越国三宗（青池/金羽/修越）｜宋廷｜道统（明阳/太阴/北寰/都仙…）｜妖族水府…
- 每势力：**一句话定位 + 立场关系**（盟/敌/附庸，箭头图）+ 成员列表（按 tier 排）+ 核心人物
- 势力间关系数据可先从 roster notes 抽取关键词共现半自动生成，人工确认

### 3.4 力量体系页（本书特色，读者高频查询）

- **境界阶梯图**（纵向金字塔）：练气→胎息→筑基→紫府（金丹）→真人/真君→道胎/仙位…按原文考证补全，每级标注代表人物（点击跳卡）
- **道统对照**：明阳（日/火/雷系…）vs 太阴 vs 各宗门道统，各自特点、代表功法、仙基案例
- **仙基图鉴**：玄雷泊（李清虹）、松上雪（李曦峻）、天齐满（刘长迭）…→ 归属人物
- 数据来源：roster notes 已含大量"仙基『X』""《功法名》"信息，可程序抽取 + 人工校对

## 四、关系网可视化方案（复杂网络怎么让用户看清）

调研结论：797 节点全铺开不可读（力导向图 >100 节点即混乱）。采用**三级缩放**：

1. **卡内局部网**（默认入口）：单人物 1 度邻接（≤30 节点），ECharts graph + force，`emphasis.focus:'adjacency'` 悬停聚焦
2. **家族网**：李家单族视图（按世代分层布局代替纯力导向——家族文用"辈分分层图"比弹簧图清楚得多，参考红楼家族树：横轴辈分、纵轴支系），可点击支系折叠
3. **全局网**（给重度读者）：仅 tier1+2（≈400），按势力 category 着色 + 图例开关关系类型（血缘/师徒/婚姻/敌对各一色），双击节点进卡

技术：ECharts 单文件本地引入（~1MB，零构建），uTools 环境 file:// 可用；关系类型数据需在构建期从 timeline/notes 抽取标注（目前 relationships 无类型字段——**新增 relationType: kinship|master|marriage|foe|ally**）。

## 五、uTools 交互适配

- subInput = 搜索（现状保留）；页面顶部 Tab：**人物｜世家｜势力｜体系**（四分类切换）
- `onPluginEnter` payload 直接跳对应实体深链（`人物:李曦明`）
- 剧透开关放头部齿轮（记忆到 localStorage）
- 键盘：↑↓ 选人 Enter 进卡 Esc 返回（已实现）+ Tab 键循环切分类

### 7.1 读者角色审阅
- **t2 的 oneLiner 不可直接当速答**：大量以"仅提及：…""（提及）…""535番外：…"开头的笔记体，读者要读两遍才懂。需批量改写为"谁+身份+与主线关系"速答句；"仅提及"应转为独立的**戏份徽章**（仅提及/出场过/重要配角/核心）而不是混进一句话里
- **防剧透必须覆盖三处**：status 徽章、timeline 后半段、stages 后半段（尤其"陨落"信息）；剧透模式默认开
- 世代徽章链（李家7世·曦字辈）很好，但 t3 的 397 人里 274 人无世代/势力任何锚点，列表里就是光秃秃的名字——至少补"首现章节"列

### 7.2 前端工程师审阅
- 四 Tab + 详情页结构可行；**797 行列表必须分页**（50/页 + 筛选），不做虚拟滚动（uTools 场景过度设计）
- ECharts 单文件 ~1MB，本地引入 file:// 可用；但**只在详情卡和世家页挂载**，列表页不加载
- uTools 默认窗口窄（~500-800px），全屏可到 1200px+：**布局需两档响应**（<700 单栏 / ≥700 详情双栏）；立绘 108px 窄窗占宽过大 → 可点击放大为浮层
- cultivation 字段现有"素材未明言境界（修有神通…）"这类**元文本必须清洗**（数据规则：没有就空串，说明进侧写）

### 7.3 数据工程师审阅
- 新增字段与产出路径：
  - `oneLiner` 改写 + `toProtagonist` + `stages` + `visualLine`：t1 从 timeline+dossier 精修（1-2 批子代理）；**t2 从 rosterNotes 批量提炼**（notes 已含身份/关系/事件原料，每批 4 人 × ~10 批）；t3 不做（只保起止章节），明确"不为无证据者编造"
  - `relationType`：t1 关系 24 组人工+规则；t2 关系需先从 notes 抽取（成本高 → 放 P3）
  - 势力从字符串数组升级为**实体**：13 个，成员反查自动聚合，oneLiner/stages 半自动+人工
- 一次性把 t2 的 376 人 oneLiner/stages 全做完再上线，还是 t1 先行？**建议分层交付**：t1 全量 → t2 按提及次数降序分批（前 100 先做）

### 7.4 AI 生图师审阅
- 现有 oneLiner 是剧情句不是视觉句，**不能直接当生图 prompt**；需独立的 `visualLine`（见 §9）
- 同人物多阶段立绘的一致性靠**固定特征锚**（瞳色/标志物/异象）跨阶段复用；CogView 无角色记忆，锚点必须每次写进 prompt
- 水印：CogView-4 右下角印章水印已成事实，定基调时一并决定（接受 / 后期裁切）
- 生图验收固定走 GLM-4.5V base64 质检（特征核对表模式）

## 九、数据 Schema v2：一句话人设 + 发展脉络 + 成图锚点

### 9.1 双句分离原则

**oneLiner（读者速答句）与 visualLine（生图视觉句）必须分开**——前者要"与主线的关系"，后者只要"看得见的东西"。强行一句两用会两头都不好。


## 11. 框架决策（替代 §五"10 文件经典 script"方案）

**已定：Vue 3 + Vite + vite-plugin-singlefile**。理由：v2 核心复杂度是全局联动（阅读进度→全 App 打码重算），响应式 store 天然匹配；uTools 打包管线复用摸鱼热搜插件经验（dev 5173 开发者模式 / dist 单文件生产）；**不加 UI 组件库**（仙侠定制样式与库默认风格互斥）。旧 `plugin/`（原生 JS 版）保留对照，`plugin-src/` 为唯一前端工程。

file:// 约束解法随之更新：singlefile 把 JS/CSS 全内联进 index.html（115KB），ES module 不可用问题不再存在；hash 路由/pushState 限制仍有效（详情是 overlay 暂不需要路由）。
