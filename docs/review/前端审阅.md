### file:// 环境四条硬约束（决定后面所有实现方式）

1. **ES Modules 不可用**：`<script type="module">` 与 `import`/`export` 在 `file://` 下被 Chromium 的 CORS 策略拦截（origin 为 null）。模块拆分只能用**按序加载的经典 `<script>` + window 命名空间**（或 IIFE）。
2. **`history.pushState` 不可用**：`file://` 下 origin 为 null，`pushState(url)` 抛 `SecurityError`。hash 路由只能用 **`location.hash` 赋值 + `hashchange` 事件**（纯 hash 修改不经过 pushState 的 URL 校验，实测可行）。
3. **动态 `import()` 同样被禁**：ECharts 懒加载必须自写 `<script>` 注入 loader（见 §3 组件）。
4. **uTools 插件退出即页面销毁**：`location.hash` 不跨会话保留。深链恢复需要 `localStorage` 存"最后路由"，`onPluginEnter` 时读取或被 payload 覆盖。

## 二、ECharts 三级缩放方案专审（§四）

### 2.1 卡内局部网 — 可行，最低风险

- 数据：`relationships`（出边）+ `referrers`（入边，preload 已算好，上限30）→ 邻接 ≤38 节点，符合"≤30"设计（可截断）。force 布局 30 节点瞬时完成。
- 交互：`emphasis.focus:'adjacency'`、节点 `click` → `openDetail(id)`。注意设计说"双击节点进卡"用于全局网、卡内单击即可——两者统一用单击更顺（ECharts `chart.on('click')`，`params.dataType==='node'` 判断）。
- **坑**：详情页每次 `render()` 都是 `$main.innerHTML` 整体重写，图表实例必须先 `chart.dispose()`（或惰性单例 + `resize`），否则快速切人会泄漏 DOM/定时器。建议 `43-comp-chart.js` 内做实例登记表，视图卸载钩子里统一销毁。

### 2.2 家族辈分分层 — 技术可行，但推荐"HTML 为主、图为辅"

`layout:'none'` + 自算坐标的正确做法：

```js
// 每个节点: x = 世代序号 * colW(约140), y = 行内序号 * rowH(约46)
// 11 世代 → 画布宽 ~1540px，超过 uTools 窗宽 → 必须 roam:true + 初始 fit（zoom 按 window 宽自适应）
series: [{ type:'graph', layout:'none', roam:true,
  edgeSymbol:['none','arrow'], edgeCurveness:0.25,
  label:{show:true, formatter:'{b}'}, symbolSize: 按 tier/mentions 缩放 }]
```

可行，但三个不稳定因素：
1. **边类型缺失**：184 条边全是 t1 视角的自由文本关系（"父亲""堂兄（幼年照拂教导）""连襟（魏廷大将军）"），无 `relationType`。分层图里婚姻/兄弟横边与父子纵边混画，交叉严重且无法按类型过滤（图例开关失效）。
2. **多父/姻亲不是树**：同一人可被多个 t1 的 relationships 指到，坐标按世代行排布后，边只能画曲线，11 列 × 数十行的画布上可读性存疑——这正是红楼家族树类项目最终都选"表格式树"的原因。
3. uTools 窄窗（~800px）里 1540px 画布只能 roam 缩放看，与 §8.5 纵表"一屏扫世代"的诉求重叠。

**更稳的替代（建议采纳）**：§8.5 的 HTML/CSS 世代纵表**就是家族视图的主实现**（成本 1 天、可读性最高、天然支持点击进卡与行折叠）；ECharts 分层图作为世家页内的可选切换（"谱系图模式"），且**等 relationType 抽取完成后再上**（纵轴支系聚类可以简单按"同父分组"排 y，避免 force 的随机性）。另一个零依赖备选：纵表容器内嵌一个手写 SVG（`<line>` + 绝对定位节点），比 ECharts graph 更可控——如果只需要"家主干线竖线高亮 + 支系缩进"，HTML 缩进树 + CSS 连接线是最稳的，不必动 ECharts。

### 2.3 全局网 — 性能可行，数据不可行

- 性能：400 节点 force（repulsion≈120、edgeLength≈40、gravity≈0.08）在 Electron 下 init 200-500ms，交互流畅；按 faction category 着色 + legend 显隐是 ECharts 原生能力，无风险。
- **数据**：t2 376 人 relationships 全空。现在上线"tier1+2 全局网"= 24 个连通分量 + 376 个孤立点，视觉上是噪音。设计文档 §六 P5 把它排在最后是对的，但 **W1-W6 工作量表里没有任何"t2 关系抽取"批次**（只有 t1 的 relationType 24 组）——这是计划缺口，见 P0-1。
- 交互补充：dblclick 进卡用 `chart.on('dblclick')`（ECharts 支持），但要与单击聚焦（`emphasis.focus`）并存时注意单击展开邻接、双击跳转的提示文案，否则用户单击后以为没反应。

## 三、防剧透与全局态专审（§8.1/§8.4/§九）

现有代码**零防剧透**（status 徽章直出），全部为增量。落地细节：

1. **判定函数统一为一个**（建议 `30-spoiler.js`）：
   ```js
   // progress = localStorage 阅读进度（默认 0 = 未读，剧透模式默认开）
   isSpoiler = {
     status: s => s === '陨落',                          // 24人有status；死亡章节未知 → 一律打码
     stage:  st => st.spoiler === true || st.chapterStart > progress,
     event:  ev => ev.chapter > progress,                // 替代文档里含糊的"timeline 后半段"
   }
   ```
   文档 §9.1 写的"章节段 > 阅读进度锚点"是 stages 的规则，但 timeline 的"后半段"没有定义——**建议统一为同一把尺子（章节号 > progress）**，UI 上一个进度输入框同时管三处，用户心智一致。需拍板（P0-3）。
2. **全局开关 O(1) 切换**：不要在开关时重渲染。容器挂 class，CSS 级联控制：
   ```css
   body.hide-spoiler .spoiler-blur { filter:blur(5px); user-select:none; background:var(--mask); }
   body.hide-spoiler .spoiler-blur.reveal { filter:none; user-select:auto; background:transparent; }
   ```
   开关只 `document.body.classList.toggle` + localStorage。**局部 reveal 与全局的关系**：全局关（显示剧透）时全部直出；全局重新打开时清除所有 `.reveal`（遍历移除，一次性 O(n) 可接受）。
3. **泄露面修补**：blur 只是视觉层——文本仍可被框选复制、仍被屏幕阅读器读出。模糊态必须 `user-select:none`（上面 CSS 已含）；`.spoiler-blur` 包裹的节点文本不要进 `title`/`aria-label`。这是 P1-9。
4. **oneLiner 侧漏（实测 31 人）**：t2/t3 的笔记体 oneLiner 里直接混着"陨落/身死/被杀"。前端无法机械打码句中子串——**规则必须写进 W3/W4 数据批次：oneLiner 不得含结局信息，结局只进 stages/status**。若不立此规矩，速答区（永远直接可见）就是防剧透体系的洞（P0-3 范围）。
5. **进度锚点 UI**：齿轮弹层里一个数字输入（1-1604）+ 剧透开关。存 `localStorage('spoiler.on')` / `('spoiler.progress')`，键名加书 id 前缀防多书串扰。

## 五、现有代码改造路径

### 5.1 现状与差距评估

现有 app.js（313 行）= `state` 单例 + `render()` 三分支（books/list/detail）+ 字符串模板 + 事件后绑定。**可保留的资产**：esc 转义、`.sect` 折叠区模式、搜索打分逻辑、referrers 反查、键盘导航骨架、浏览器 fallback 双环境策略——约占 v2 需求的 25-30%。**缺的**：路由、Tab 骨架、四个新视图、时间带/图表/浮层三类组件、防剧透系统、分页、持久化。v2 全量预计 **1800-2400 行 / 10-14 个文件 / 7-10 人日**（不含数据批次）。

**要拆模块吗？要。** 313 行硬塞到 2000+ 行后，单文件里五个视图的模板字符串互相踩踏、ECharts 实例生命周期无处安放，维护成本会立刻失控。但拆法受 file:// 约束（P1-8）：经典 script + window 命名空间，禁止 import/export。
